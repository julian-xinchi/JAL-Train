# synopsys的Z01X的fault_coverage.rpt里有个Promotiontable，如何理解？

可以把 Z01X 的 **`PromotionTable`** 理解成：

> **当同一个 fault 在多次 fault simulation / 多个 test 中得到不同 status 时，规定这些 status 如何合并（merge）的规则表。**

这点非常重要：**PromotionTable 不是用来“提升 fault coverage”的表**，这里的 *promotion* 更接近 **fault status promotion / status merging**。公开的 Z01X 相关资料也明确说，多个 fault class/status 之间的交互由 Promotion Table 控制；多次测试运行时，它用于定义 fault status 的合并方式。([TU Delft Repository][1])

### 1. 为什么需要 PromotionTable？

假设一个 fault：

```text
Fault F1
```

你跑了多个 test：

```text
Test 1 → ND
Test 2 → ND
Test 3 → DD
```

那么最终 `F1` 应该是什么状态？

显然不能简单地说“最后一次结果覆盖前面的结果”，而应该：

```text
ND + DD → DD
```

因为这个 fault **至少被一个 test 检测到了**。

PromotionTable 就是规定这种：

```text
旧状态 + 新状态 → 最终状态
```

的规则。

---

### 2. 可以把它理解成一个二维查表

概念上：

```text
                 New status
              NN   NP   ND   PN   OP   ON   OD
           +------------------------------------
Current NN |  ?    ?    ?    ?    ?    ?    ?
       NP  |  ?    ?    ?    ?    ?    ?    ?
       ND  |  ?    ?    ?    ?    ?    ?    ?
       PN  |  ?    ?    ?    ?    ?    ?    ?
       OP  |  ?    ?    ?    ?    ?    ?    ?
       ON  |  ?    ?    ?    ?    ?    ?    ?
       OD  |  ?    ?    ?    ?    ?    ?    ?
```

每一个格子表示：

```text
Current Status + New Status
              ↓
        Merged Status
```

例如公开的 Z01X/SFF 示例中：

```text
ND + OP → OD
```

或者：

```text
PN + OP → ON
```

这就是 PromotionTable 在干的事情。([DVCon 论文集][2])

---

### 3. 对你实际看 `fault_coverage.rpt` 最重要的一点

假设：

```text
Test A:
F001 → ND

Test B:
F001 → DD
```

最终 fault coverage report 里：

```text
F001 → DD
```

并不是因为 Test B 单独决定了结果，而是 Z01X 根据 PromotionTable 做了：

```text
             Test A
               │
               ▼
             F001
               │
              ND
               │
               │  merge
               ▼
              DD
               ▲
               │
             DD
               │
             Test B
```

即：

```text
ND + DD → DD
```

所以如果你是在分析 **为什么一个 fault 最终被归类为 DD / ND / ...**，就需要看 PromotionTable。

---

### 4. 为什么叫 Promotion？

可以把它粗略理解成 **status 向“更强”的状态升级**。

例如：

```text
Not detected
      ↓
Potentially detected
      ↓
Detected
```

一次 test 中可能只能得到比较弱的 status；另一次 test 提供了更强的 evidence，那么 fault 的最终 status 可以被 **promoted**。

但要注意：

> **不是简单地认为 DD 永远最高、所有 status 都按一个固定优先级排序。**

因为 Z01X 的 fault classification 比较复杂，不同 status 的组合有专门的规则。公开资料也特别提到，Z01X 有多个 built-in status groups，custom fault classes 也可以通过 fault specification 定义，而这些 class 之间的交互由 PromotionTable 控制。([TU Delft Repository][1])

### 5. 和你前面问的 IA 联系起来

你之前问过：

> Z01X 中 `IA (Illegal Access)` 是什么意思？

这个就能和 PromotionTable 联系起来。

假设某个 fault 在一次 test 中：

```text
F001 → IA
```

另一次 test：

```text
F001 → DD
```

最终到底显示什么，**不能仅凭“DD 比 IA 好”来猜**，而要看 Z01X 当前使用的 PromotionTable 对：

```text
IA + DD
```

是怎么定义的。

这也是为什么如果你正在分析 `fault_coverage.rpt`，**PromotionTable 本身非常有价值**。

---

### 6. 一个很实用的理解方式

你可以把 Z01X 的整个 multi-test fault coverage 流程想成：

```text
             Test 1
               │
               ▼
          Fault simulation
               │
               ▼
        Status of each fault
               │
               │
             merge
               │
               ▼
       ┌─────────────────┐
       │ Promotion Table │
       └─────────────────┘
               ▲
               │
             merge
               │
               ▲
        Status from Test 2
               │
               ▲
        Status from Test 3
               │
              ...
               │
               ▼
        Final fault status
               │
               ▼
        Fault coverage
```

所以：

**PromotionTable = 多个 test / 多次 fault simulation 结果的 status 合并规则。**

# 既然Z01X每次都会对DUT生成一个fault，并仿真good machine/faulty machine对比，但仿真速度为什么比普通的仿真regression速度还更快？


这里有一个关键点需要纠正：**Z01X 并不是简单地“每个 fault 都完整跑一遍 good machine + faulty machine，然后逐个比较”**。如果真是这种 brute-force 方法，速度确实会比普通 regression 慢很多个数量级。

Z01X 之所以能做到 fault simulation，核心就在于它采用了专门的 **fault simulation / fault propagation 加速机制**。

### 1. 普通理解的方式其实是这样

假设 DUT 有 100 万个 faults：

```text
             Good
              │
              ├── Test → simulation
              │
              ▼
          good result

F001 → Faulty simulation → compare
F002 → Faulty simulation → compare
F003 → Faulty simulation → compare
...
F1M → Faulty simulation → compare
```

如果真的这样做：

```text
1 个 fault = 1 次完整 RTL simulation
```

那么：

```text
100 万 faults × 1 次 regression
```

显然是不可能接受的。

---

# 2. 实际 fault simulation 并不是这么干

Fault simulation 的基本思想是：

> **Good machine 只需要模拟一次，然后在同一个 simulation 中并行处理大量 faults。**

可以粗略理解成：

```text
                  Test stimulus
                       │
                       ▼
                ┌─────────────┐
                │ Good Machine│
                └──────┬──────┘
                       │
                  good values
                       │
             ┌─────────┴─────────┐
             │                   │
             ▼                   ▼
          Fault #1             Fault #2
             │                   │
             ▼                   ▼
        fault effect         fault effect
             │                   │
             └─────────┬─────────┘
                       ▼
                  observation
                       │
                       ▼
                fault detected?
```

也就是说，**Good Machine 的仿真结果可以被大量 fault 共享**。

这和你说的：

> good machine / faulty machine 对比

概念上是对的，但不是：

> 每个 fault 单独启动一个完整 simulator。

---

# 3. Fault simulation 最核心的优化：fault collapsing / parallelism

例如某个逻辑：

```text
A ──┐
    AND ── Y
B ──┘
```

正常 good machine 计算：

```text
A = 1
B = 1
Y = 1
```

现在假设有：

```text
SA0(A)
SA1(A)
SA0(B)
SA1(B)
SA0(Y)
SA1(Y)
```

并不需要真的分别跑 6 次。

Fault simulator 可以在内部维护：

```text
Good value
+
fault-related information
```

甚至一次 machine word 中并行编码多个 faults。

例如概念上：

```text
32-bit word

bit 0  → fault F001
bit 1  → fault F002
bit 2  → fault F003
...
bit 31 → fault F032
```

那么一次逻辑运算就可能同时计算：

```text
F001 ~ F032
```

这就是 **parallel fault simulation** 的核心思想之一。

---

# 4. 还有一个非常重要的原因：Fault 不一定需要“从头跑到尾”

假设某个 fault：

```text
F001
```

在时间：

```text
100 ns
```

已经被观察点检测出来：

```text
fault effect → PO
```

那么：

> **这个 fault 后面的 simulation 已经没有必要继续关注它。**

它可以直接被标记：

```text
F001 → Detected
```

然后从 active fault set 中删除。

这就是你前面看到的 Z01X 中各种：

```text
fault dropping
$fs_drop_status()
```

背后的重要思想之一。

概念上：

```text
100000 faults
      │
      ▼
simulation
      │
      ├── 20000 detected → drop
      │
      ├── 10000 redundant → drop
      │
      ├── ...
      │
      ▼
remaining active faults
      │
      ▼
继续 simulation
```

因此真正参与后续计算的 fault 数量会越来越少。

---

# 5. 这也是为什么你看到 `$fs_drop_status()` 很重要

你上一条提到：

```systemverilog
$fs_get_status();
$fs_drop_status("xx");
```

现在把它放到整个 fault simulation 体系里，就比较容易理解了。

`$fs_drop_status()` 本质上就是在 fault simulation 的过程中，对 fault status 进行管理。

例如：

```text
              Fault pool
                  │
        ┌─────────┴─────────┐
        │                   │
     active             detected
        │                   │
        │              $fs_drop_status
        │                   │
        └────── simulation ─┘
```

已经满足某种条件的 fault，就不需要继续作为 active fault 参与后面的 fault simulation。

---

# 6. Z01X 还有一个巨大优势：它不是普通 RTL simulator

这是另一个非常重要的区别。

普通 regression：

```text
RTL
 ↓
compile/elaboration
 ↓
event-driven simulation
 ↓
每个 signal/event 都正常计算
 ↓
dump/check/assert/etc.
```

Z01X 的 fault simulation engine 是针对：

```text
fault simulation
fault propagation
fault classification
fault dropping
fault grading
```

专门优化的。

它不会把每一个 faulty machine 都当成一个完整的 RTL simulator 来跑。

可以粗略理解为：

```text
普通 simulation：

       DUT
        │
        ▼
   Event simulator
        │
        ▼
   所有 RTL behavior


Z01X：

       DUT
        │
        ▼
   Good machine
        │
        ▼
   Fault simulation engine
        │
    ┌───┼────────┐
    ▼   ▼        ▼
   F1   F2  ...  Fn
    │   │        │
    └───┼────────┘
        ▼
   Fault propagation
        │
        ▼
   Fault grading
```

所以两者不能简单按“仿真了多少个 machine”比较。

---

# 7. 为什么甚至可能比普通 regression 更快？

假设你的普通 regression 一个 testcase：

```text
T = 100 seconds
```

而 Z01X fault simulation：

```text
Good machine ≈ 一次
Fault simulation ≈ 专用并行 fault engine
```

虽然它做了大量 fault work，但这些 work 是高度共享的。

尤其当：

* fault 很容易被 detect；
* fault dropping 很有效；
* fault list 可以进行 collapsing；
* faults 可以并行模拟；
* stimulus 本身比较短；
* fault simulation engine 针对 gate/RTL 结构进行了优化；

那么可能出现：

```text
普通 RTL regression
    100 s

Z01X fault simulation
     20 s
```

这并不矛盾。

**“处理的 fault 数量多” ≠ “进行了同样数量的完整 RTL simulation”。**

---

# 8. 一个很直观的类比

假设你要测试 1000 个学生的答案。

### 普通方法

老师：

```text
学生1 → 从头批改
学生2 → 从头批改
...
学生1000 → 从头批改
```

### Fault simulation

先把标准答案：

```text
Good machine
```

准备好一次。

然后：

```text
学生1的错误
学生2的错误
学生3的错误
...
```

同时分析这些错误**在哪一步开始影响答案**。

一个错误一旦已经明确影响最终答案：

```text
Detected → 不再继续跟踪
```

这就是 fault simulation 为什么能够高效的直觉。

## 9. 不过有一点值得你特别注意

你说：

> “Z01X 每次都会对 DUT 生成一个 fault，并仿真 good machine/faulty machine 对比”

如果这是你从 Z01X 的某个文档/报告中看到的描述，那么它很可能是在讲 **conceptual fault simulation model**，而不是说：

> Z01X 实际启动一个 simulator process，然后把 DUT 完整复制一份，再跑一次。

实际实现可能是 **fault-parallel / fault-dynamic / fault propagation** 等多种优化机制的组合。

而你前面提到的：

```text
TestList
OBS_LIST
DIAG_LIST
$fs_compare()
$fs_set_status()
$fs_get_status()
$fs_drop_status()
PromotionTable
```

其实正好说明你的 Z01X flow **在 fault simulation engine 之外，还有一套 fault status / classification / dropping 机制**。

所以如果你现在想真正弄清楚：

> **“Z01X 到底是怎么做到一个 test 同时模拟几十万/几百万 faults 的？”**

下一步最值得看的其实不是 `fault_coverage.rpt`，而是 **Z01X 的 simulation log / run log 中关于 fault simulation mode、fault grouping、fault dropping、parallel fault simulation 的信息**。这些信息可以直接判断你的环境到底采用了哪种 fault simulation 加速方式。
