# synopsys的Z01X的fault_coverage.rpt里有个Promotiontable，如何理解？

可以把 Z01X 的 **`PromotionTable`** 理解成：

> **当同一个 fault 在多次 fault simulation / 多个 test 中得到不同 status 时，规定这些 status 如何合并（merge）的规则表。**

这点非常重要：**PromotionTable 不是用来“提升 fault coverage”的表**，这里的 *promotion* 更接近 **fault status promotion / status merging**。公开的 Z01X 相关资料也明确说，多个 fault class/status 之间的交互由 Promotion Table 控制；多次测试运行时，它用于定义 fault status 的合并方式。([TU Delft Repository][1])

### 1. 为什么需要 PromotionTable？

假设一个 fault：

```text
Fault F1
```

你跑了多个 test：

```text
Test 1 → ND
Test 2 → ND
Test 3 → DD
```

那么最终 `F1` 应该是什么状态？

显然不能简单地说“最后一次结果覆盖前面的结果”，而应该：

```text
ND + DD → DD
```

因为这个 fault **至少被一个 test 检测到了**。

PromotionTable 就是规定这种：

```text
旧状态 + 新状态 → 最终状态
```

的规则。

---

### 2. 可以把它理解成一个二维查表

概念上：

```text
                 New status
              NN   NP   ND   PN   OP   ON   OD
           +------------------------------------
Current NN |  ?    ?    ?    ?    ?    ?    ?
       NP  |  ?    ?    ?    ?    ?    ?    ?
       ND  |  ?    ?    ?    ?    ?    ?    ?
       PN  |  ?    ?    ?    ?    ?    ?    ?
       OP  |  ?    ?    ?    ?    ?    ?    ?
       ON  |  ?    ?    ?    ?    ?    ?    ?
       OD  |  ?    ?    ?    ?    ?    ?    ?
```

每一个格子表示：

```text
Current Status + New Status
              ↓
        Merged Status
```

例如公开的 Z01X/SFF 示例中：

```text
ND + OP → OD
```

或者：

```text
PN + OP → ON
```

这就是 PromotionTable 在干的事情。([DVCon 论文集][2])

---

### 3. 对你实际看 `fault_coverage.rpt` 最重要的一点

假设：

```text
Test A:
F001 → ND

Test B:
F001 → DD
```

最终 fault coverage report 里：

```text
F001 → DD
```

并不是因为 Test B 单独决定了结果，而是 Z01X 根据 PromotionTable 做了：

```text
             Test A
               │
               ▼
             F001
               │
              ND
               │
               │  merge
               ▼
              DD
               ▲
               │
             DD
               │
             Test B
```

即：

```text
ND + DD → DD
```

所以如果你是在分析 **为什么一个 fault 最终被归类为 DD / ND / ...**，就需要看 PromotionTable。

---

### 4. 为什么叫 Promotion？

可以把它粗略理解成 **status 向“更强”的状态升级**。

例如：

```text
Not detected
      ↓
Potentially detected
      ↓
Detected
```

一次 test 中可能只能得到比较弱的 status；另一次 test 提供了更强的 evidence，那么 fault 的最终 status 可以被 **promoted**。

但要注意：

> **不是简单地认为 DD 永远最高、所有 status 都按一个固定优先级排序。**

因为 Z01X 的 fault classification 比较复杂，不同 status 的组合有专门的规则。公开资料也特别提到，Z01X 有多个 built-in status groups，custom fault classes 也可以通过 fault specification 定义，而这些 class 之间的交互由 PromotionTable 控制。([TU Delft Repository][1])

---

### 5. 和你前面问的 IA 联系起来

你之前问过：

> Z01X 中 `IA (Illegal Access)` 是什么意思？

这个就能和 PromotionTable 联系起来。

假设某个 fault 在一次 test 中：

```text
F001 → IA
```

另一次 test：

```text
F001 → DD
```

最终到底显示什么，**不能仅凭“DD 比 IA 好”来猜**，而要看 Z01X 当前使用的 PromotionTable 对：

```text
IA + DD
```

是怎么定义的。

这也是为什么如果你正在分析 `fault_coverage.rpt`，**PromotionTable 本身非常有价值**。

---

### 6. 一个很实用的理解方式

你可以把 Z01X 的整个 multi-test fault coverage 流程想成：

```text
             Test 1
               │
               ▼
          Fault simulation
               │
               ▼
        Status of each fault
               │
               │
             merge
               │
               ▼
       ┌─────────────────┐
       │ Promotion Table │
       └─────────────────┘
               ▲
               │
             merge
               │
               ▲
        Status from Test 2
               │
               ▲
        Status from Test 3
               │
              ...
               │
               ▼
        Final fault status
               │
               ▼
        Fault coverage
```

所以：

**PromotionTable = 多个 test / 多次 fault simulation 结果的 status 合并规则。**

# 既然Z01X每次都会对DUT生成一个fault，并仿真good machine/faulty machine对比，但仿真速度为什么比普通的仿真regression速度还更快？


这里有一个关键点需要纠正：**Z01X 并不是简单地“每个 fault 都完整跑一遍 good machine + faulty machine，然后逐个比较”**。如果真是这种 brute-force 方法，速度确实会比普通 regression 慢很多个数量级。

Z01X 之所以能做到 fault simulation，核心就在于它采用了专门的 **fault simulation / fault propagation 加速机制**。

### 1. 普通理解的方式其实是这样

假设 DUT 有 100 万个 faults：

```text
             Good
              │
              ├── Test → simulation
              │
              ▼
          good result

F001 → Faulty simulation → compare
F002 → Faulty simulation → compare
F003 → Faulty simulation → compare
...
F1M → Faulty simulation → compare
```

如果真的这样做：

```text
1 个 fault = 1 次完整 RTL simulation
```

那么：

```text
100 万 faults × 1 次 regression
```

显然是不可能接受的。

---

# 2. 实际 fault simulation 并不是这么干

Fault simulation 的基本思想是：

> **Good machine 只需要模拟一次，然后在同一个 simulation 中并行处理大量 faults。**

可以粗略理解成：

```text
                  Test stimulus
                       │
                       ▼
                ┌─────────────┐
                │ Good Machine│
                └──────┬──────┘
                       │
                  good values
                       │
             ┌─────────┴─────────┐
             │                   │
             ▼                   ▼
          Fault #1             Fault #2
             │                   │
             ▼                   ▼
        fault effect         fault effect
             │                   │
             └─────────┬─────────┘
                       ▼
                  observation
                       │
                       ▼
                fault detected?
```

也就是说，**Good Machine 的仿真结果可以被大量 fault 共享**。

这和你说的：

> good machine / faulty machine 对比

概念上是对的，但不是：

> 每个 fault 单独启动一个完整 simulator。

---

# 3. Fault simulation 最核心的优化：fault collapsing / parallelism

例如某个逻辑：

```text
A ──┐
    AND ── Y
B ──┘
```

正常 good machine 计算：

```text
A = 1
B = 1
Y = 1
```

现在假设有：

```text
SA0(A)
SA1(A)
SA0(B)
SA1(B)
SA0(Y)
SA1(Y)
```

并不需要真的分别跑 6 次。

Fault simulator 可以在内部维护：

```text
Good value
+
fault-related information
```

甚至一次 machine word 中并行编码多个 faults。

例如概念上：

```text
32-bit word

bit 0  → fault F001
bit 1  → fault F002
bit 2  → fault F003
...
bit 31 → fault F032
```

那么一次逻辑运算就可能同时计算：

```text
F001 ~ F032
```

这就是 **parallel fault simulation** 的核心思想之一。

---

# 4. 还有一个非常重要的原因：Fault 不一定需要“从头跑到尾”

假设某个 fault：

```text
F001
```

在时间：

```text
100 ns
```

已经被观察点检测出来：

```text
fault effect → PO
```

那么：

> **这个 fault 后面的 simulation 已经没有必要继续关注它。**

它可以直接被标记：

```text
F001 → Detected
```

然后从 active fault set 中删除。

这就是你前面看到的 Z01X 中各种：

```text
fault dropping
$fs_drop_status()
```

背后的重要思想之一。

概念上：

```text
100000 faults
      │
      ▼
simulation
      │
      ├── 20000 detected → drop
      │
      ├── 10000 redundant → drop
      │
      ├── ...
      │
      ▼
remaining active faults
      │
      ▼
继续 simulation
```

因此真正参与后续计算的 fault 数量会越来越少。

---

# 5. 这也是为什么你看到 `$fs_drop_status()` 很重要

你上一条提到：

```systemverilog
$fs_get_status();
$fs_drop_status("xx");
```

现在把它放到整个 fault simulation 体系里，就比较容易理解了。

`$fs_drop_status()` 本质上就是在 fault simulation 的过程中，对 fault status 进行管理。

例如：

```text
              Fault pool
                  │
        ┌─────────┴─────────┐
        │                   │
     active             detected
        │                   │
        │              $fs_drop_status
        │                   │
        └────── simulation ─┘
```

已经满足某种条件的 fault，就不需要继续作为 active fault 参与后面的 fault simulation。

---

# 6. Z01X 还有一个巨大优势：它不是普通 RTL simulator

这是另一个非常重要的区别。

普通 regression：

```text
RTL
 ↓
compile/elaboration
 ↓
event-driven simulation
 ↓
每个 signal/event 都正常计算
 ↓
dump/check/assert/etc.
```

Z01X 的 fault simulation engine 是针对：

```text
fault simulation
fault propagation
fault classification
fault dropping
fault grading
```

专门优化的。

它不会把每一个 faulty machine 都当成一个完整的 RTL simulator 来跑。

可以粗略理解为：

```text
普通 simulation：

       DUT
        │
        ▼
   Event simulator
        │
        ▼
   所有 RTL behavior


Z01X：

       DUT
        │
        ▼
   Good machine
        │
        ▼
   Fault simulation engine
        │
    ┌───┼────────┐
    ▼   ▼        ▼
   F1   F2  ...  Fn
    │   │        │
    └───┼────────┘
        ▼
   Fault propagation
        │
        ▼
   Fault grading
```

所以两者不能简单按“仿真了多少个 machine”比较。

---

# 7. 为什么甚至可能比普通 regression 更快？

假设你的普通 regression 一个 testcase：

```text
T = 100 seconds
```

而 Z01X fault simulation：

```text
Good machine ≈ 一次
Fault simulation ≈ 专用并行 fault engine
```

虽然它做了大量 fault work，但这些 work 是高度共享的。

尤其当：

* fault 很容易被 detect；
* fault dropping 很有效；
* fault list 可以进行 collapsing；
* faults 可以并行模拟；
* stimulus 本身比较短；
* fault simulation engine 针对 gate/RTL 结构进行了优化；

那么可能出现：

```text
普通 RTL regression
    100 s

Z01X fault simulation
     20 s
```

这并不矛盾。

**“处理的 fault 数量多” ≠ “进行了同样数量的完整 RTL simulation”。**

---

# 8. 一个很直观的类比

假设你要测试 1000 个学生的答案。

### 普通方法

老师：

```text
学生1 → 从头批改
学生2 → 从头批改
...
学生1000 → 从头批改
```

### Fault simulation

先把标准答案：

```text
Good machine
```

准备好一次。

然后：

```text
学生1的错误
学生2的错误
学生3的错误
...
```

同时分析这些错误**在哪一步开始影响答案**。

一个错误一旦已经明确影响最终答案：

```text
Detected → 不再继续跟踪
```

这就是 fault simulation 为什么能够高效的直觉。

---

## 9. 不过有一点值得你特别注意

你说：

> “Z01X 每次都会对 DUT 生成一个 fault，并仿真 good machine/faulty machine 对比”

如果这是你从 Z01X 的某个文档/报告中看到的描述，那么它很可能是在讲 **conceptual fault simulation model**，而不是说：

> Z01X 实际启动一个 simulator process，然后把 DUT 完整复制一份，再跑一次。

实际实现可能是 **fault-parallel / fault-dynamic / fault propagation** 等多种优化机制的组合。

而你前面提到的：

```text
TestList
OBS_LIST
DIAG_LIST
$fs_compare()
$fs_set_status()
$fs_get_status()
$fs_drop_status()
PromotionTable
```

其实正好说明你的 Z01X flow **在 fault simulation engine 之外，还有一套 fault status / classification / dropping 机制**。

所以如果你现在想真正弄清楚：

> **“Z01X 到底是怎么做到一个 test 同时模拟几十万/几百万 faults 的？”**

下一步最值得看的其实不是 `fault_coverage.rpt`，而是 **Z01X 的 simulation log / run log 中关于 fault simulation mode、fault grouping、fault dropping、parallel fault simulation 的信息**。这些信息可以直接判断你的环境到底采用了哪种 fault simulation 加速方式。


















这张图很关键，它实际上补充了 **Z01X 中 IA（Illegal Access）更准确的定义**。这里的 IA 不只是我们之前说的“fault simulation 过程中访问了未分配的 dynamic array/class”。

原文可以拆成两种情况：

> **An illegal access fault results from an unallocated dynamic array or class reference in a faulty machine.**

### 1. Faulty machine 中出现未分配的 dynamic array / class reference

也就是 fault machine 在执行 fault simulation 时，访问了一个没有正确分配的：

* dynamic array
* class reference

例如：

```systemverilog
class foo;
    ...
endclass

foo f;

initial begin
    f.xxx = ...;   // f 没有 new()
end
```

faulty machine 的执行路径因为 fault injection/propagation 产生了这种非法引用，就可能得到 **IA**。

---

### 2. Fault 被尝试“移动”到一个没有建立 fault simulation 的位置

这个其实更值得注意。原文：

> **A fault ... was attempted to be moved to a new location that was not set up for fault simulation.**

这里的 **moved to a new location** 可以理解成 Z01X 在 fault simulation 内部进行 **fault propagation / fault relocation**。

假设原来的 fault 是：

```text
     A
     |
   [fault]
     |
     B
```

fault simulation 过程中，工具可能会把 fault 的表示从一个位置传播/移动到另一个位置：

```text
original fault
      ↓
     A
      ↓
    gate
      ↓
     B   ← fault moved/propagated here
```

但是如果 `B` 这个位置**没有被建立为 fault simulation 所需要的 location**，那么这个 fault 就无法继续正常模拟，于是产生 **IA**。

所以这里的 IA 本质上是：

> **The fault simulation engine attempted to access or move a fault to a location that was not prepared/supported for fault simulation.**

---

### 3. Transient fault 是一个特别的例子

原文特别说：

> **This is the case with transient faults that are attempted to be moved to input locations, which are not supported by transient faults.**

意思是：

**Transient fault 被尝试移动到 input location，而 transient fault 不支持 input location，因此产生 IA。**

例如：

```text
       INPUT
         │
         ▼
      +-----+
      | Gate|
      +-----+
         │
         ▼
       OUTPUT
```

如果某个 transient fault 在 fault propagation 过程中被尝试移动到：

```text
INPUT
  ↑
fault
```

但 Z01X 的 transient fault model 不允许 transient fault 位于 input location，那么这个 fault 就会成为：

```text
IA (Illegal Access)
```

---

### 这也解释了一个容易误解的地方

所以 **IA 不一定意味着 DUT RTL 本身存在“非法访问”**。

更准确地说：

```text
                     Z01X Fault Simulation
                              │
                 ┌────────────┴────────────┐
                 │                         │
        Faulty machine              Fault propagation
                 │                         │
                 │                  fault moved to
                 │                  another location
                 │                         │
        unallocated                  location not
        dynamic array /              set up for
        class reference              fault simulation
                 │                         │
                 └────────────┬────────────┘
                              ↓
                         IA (Illegal Access)
```

尤其是你现在看到的这段官方定义，我会把之前对 IA 的解释修正得更准确一些：

> **IA means that the fault simulation could not continue normally because the faulty machine accessed an unallocated dynamic object, or because a fault was moved to a location that was not set up or supported for fault simulation.**

因此，在分析你们 `fault_coverage.rpt` 中的 IA 时，**不能直接把 IA 当成“DUT 有 illegal access”或者“这个 fault 没检测到”**。

特别值得检查的是：**IA fault 是不是 transient fault，以及 fault 的最终/尝试移动位置是不是 input location。** 这两点和你截图中的第二段定义是直接对应的。













# 为什么verilog RTL代码会存在dynamic object？

严格来说，**普通的 Verilog RTL 本身通常不存在 dynamic object**。你这里看到 Z01X 文档里的 **“unallocated dynamic array or class reference”**，很可能不是在说你的 DUT RTL 设计中主动使用了 SystemVerilog dynamic array/class。

关键在于要区分 **DUT RTL** 和 **fault simulation model / simulation environment**。

### 1. 普通 RTL 里通常是什么

典型 RTL：

```systemverilog
logic [31:0] data;
logic [7:0]  fifo [0:15];
logic        valid;

always_ff @(posedge clk) begin
    ...
end
```

这些都是**静态分配的仿真对象**。

即使是：

```systemverilog
logic [31:0] mem [0:1023];
```

也是固定大小的 unpacked array，并不是 dynamic array。

---

### 2. SystemVerilog 确实允许 dynamic array

例如：

```systemverilog
logic [31:0] data[];

initial begin
    data = new[1024];
end
```

这里：

```text
data
 │
 └── dynamic array
```

真正的 storage 是通过：

```systemverilog
data = new[1024];
```

动态分配的。

如果：

```systemverilog
logic [31:0] data[];

initial begin
    $display(data[0]);
end
```

此时 `data` 没有 `new[]`，就是 **unallocated dynamic array**。

---

### 3. Class 更明显

例如 verification environment 中大量使用：

```systemverilog
class transaction;
    rand bit [31:0] addr;
    rand bit [31:0] data;
endclass
```

然后：

```systemverilog
transaction tr;

initial begin
    tr = new();
end
```

如果没有：

```systemverilog
tr = new();
```

直接：

```systemverilog
tr.addr = 32'h1234;
```

就是访问一个 **unallocated/null class reference**。

这在 UVM/testbench 中非常常见。

---

### 4. 那为什么 Z01X 的 faulty machine 会碰到这些？

这正是你截图里最容易让人误解的地方。

Z01X 说的是：

> **in a faulty machine**

而不是：

> **in the DUT RTL**

Z01X 做 fault simulation 时，实际上不是简单地：

```text
RTL DUT
  ↓
普通 simulator
```

而是建立/维护一个用于 fault simulation 的 **faulty machine**。

可以粗略理解成：

```text
                Z01X
                 │
        ┌────────┴────────┐
        │                 │
   Good Machine       Faulty Machine
        │                 │
      RTL sim       RTL + fault information
                          │
                          ↓
                  fault propagation
```

Faulty machine 内部为了表示 fault、fault state、fault propagation 等信息，**可能会使用动态数据结构**。

因此：

> **“dynamic array or class reference” 很可能是 Z01X fault simulation infrastructure/model 中的数据结构，而不是你的 RTL 中存在 dynamic array/class。**

---

### 5. 还有一种情况：RTL/testbench 本身确实用了 SystemVerilog dynamic object

如果你的整个 simulation environment 是 SystemVerilog，那么 RTL、BFM、VIP、UVM、testbench、monitor 等代码中都可能出现：

```systemverilog
dynamic array
queue
associative array
class
```

特别是：

```text
UVM
  │
  ├── sequence
  ├── transaction
  ├── scoreboard
  ├── monitor
  └── driver
```

这些地方大量使用 class / dynamic data structure。

但是需要注意：

**queue / associative array 和 dynamic array 是不同的 SystemVerilog 数据类型。**

例如：

```systemverilog
int a[];          // dynamic array
int q[$];         // queue
int aa[string];   // associative array
```

所以 Z01X 文档明确写 **dynamic array or class reference**，它指的是比较具体的两类对象。

---

### 6. 对你现在这个 IA 问题，最重要的是这一点

如果你的 DUT 是正常的 synthesizable RTL，例如：

```systemverilog
module dut (...);

logic [31:0] data;
logic [7:0]  state;

always_ff @(posedge clk)
    ...

endmodule
```

那么看到：

```text
IA (Illegal Access)
```

**不能据此推断 DUT RTL 中存在 dynamic object。**

尤其你截图后半段说：

> transient faults that are attempted to be moved to input locations, which are not supported by transient faults

这反而说明 **IA 有可能完全是 Z01X fault model / fault propagation 过程产生的**：

```text
              fault
                │
                ▼
        fault propagation
                │
                ▼

                │
                ▼

                │
                ▼
               IA
```

所以如果你是在分析你们 `fault_coverage.rpt` 里的 IA，我现在更倾向于把问题分成两类：

1. **simulation infrastructure 中真的发生了 dynamic object/class reference 问题**
2. **Z01X fault propagation 把 fault 移到了不支持的位置**，尤其是 transient fault → input location

第二种其实和你截图中的第二段是直接对应的。

这张图对理解 Z01X 的 **NO (Not Observed)** 很有帮助，而且它和你前面问的 **fault collapsing / exclude / IA** 是不同层面的概念。

### 1. NO 的核心含义

原文：

> “the workload(s) blocked the activity of that fault location from propagating to an observation point”

意思是：

**fault 本身可以正常注入，但 workload 没有给它提供传播到 observation point 的条件。**

也就是说：

```text
Fault location
     │
     │ fault effect
     ▼
   logic
     │
     │  ← 被 workload 阻断
     X
     │
     ▼
Observation point
```

所以 Z01X 认为这个 fault **无法被观察到（observed）**，状态就是 **NO**。

---

### 2. 图里的例子非常典型

电路是一个 NAND：

```text
 A ─────────┐
            │
            NAND ─── OUT
 B ─────────┘
```

假设 fault 在 A：

```text
A ──[sa0/sa1 fault]──┐
                      NAND ── OUT
B ────────────────────┘
```

而 workload 中：

```text
B = 0
```

始终不变。

NAND 的逻辑：

```text
B = 0
    ↓
A = 0 → OUT = 1
A = 1 → OUT = 1
```

所以无论 A 是：

```text
good machine:    A = 0/1
faulty machine:  A = 1/0
```

最终：

```text
OUT_good   = 1
OUT_faulty = 1
```

因此 fault effect 根本传不到 OUT。

于是：

```text
A SA0/SA1
     ↓
   NAND
     ↓
   BLOCKED
     ↓
    NO
```

这就是所谓的 **dominant signal**。

---

### 3. 为什么叫 dominant signal？

对于 NAND：

```text
A ─┐
   NAND ── OUT
B ─┘
```

`B = 0` 时：

```text
OUT = ~(A & 0)
    = ~0
    = 1
```

所以 B 把 A 的影响完全盖掉了。

因此可以说：

> **B is the controlling/dominant value for the NAND gate.**

更常见的逻辑测试术语是 **controlling value**：

| Gate | Controlling value |
| ---- | ----------------: |
| AND  |                 0 |
| NAND |                 0 |
| OR   |                 1 |
| NOR  |                 1 |

所以这里 `B=0` 是 NAND 的 **controlling value**。

---

### 4. 这里的 X 为什么也可能导致 NO？

图中明确写的是：

> If B ... stays **0 or X** for the entire toggle simulation, the above fault will be NO.

这是因为 Z01X 的 fault propagation 需要一个能够区分 good/faulty machine 的逻辑传播条件。

如果 B 一直是 X：

```text
B = X
```

那么 A 上的 fault effect 也无法形成一个明确、可观察的差异传播路径。

因此 Z01X 可以把这种情况归类为 **NO**。

---

### 5. 这和“fault 没有被检测到”有什么区别？

这是 Z01X status 中一个很重要的区别。

可以粗略理解为：

```text
Fault
 │
 ├── 根本没有成功 injection
 │       → NI
 │
 ├── injection 了，但 propagation 被 workload 阻断
 │       → NO
 │
 ├── propagation 到 observation point
 │       ↓
 │     被检测到
 │       → OD / ON 等
 │
 └── fault simulation 本身遇到问题
         → IA 等
```

所以 **NO 并不是 Z01X 出错了**。

它实际上告诉你：

> **在这个 workload 下，这个 fault 的影响没有获得传播到 observation point 所需的逻辑激励。**

---

### 6. 这也能帮助理解你前面问的 IA

你前面说：

> 某几个关键 signal 可以 collapse，其中一个 signal 在 SFF 中设置为 exclude，会不会产生 IA？

这里要特别区分：

**NO：**

```text
fault location
      ↓
fault effect
      ↓
正常 propagation
      ↓
被逻辑条件阻断
      ↓
NO
```

**IA：**

```text
fault location
      ↓
fault propagation / relocation
      ↓
尝试访问一个没有 setup / 不支持的位置
      ↓
IA
```

因此，如果某个 signal 被 SFF exclude 后，只是导致 fault **无法通过 workload 传播到 observation point**，那么从你现在这份 Z01X 定义来看，更接近 **NO**，而不是 IA。

只有当这个 exclude **影响了 Z01X 对 fault location 的建立、fault relocation/collapsing 后的位置、或者 fault simulation data structure**，导致工具尝试把 fault 移到一个“不允许/未 setup”的 location，才有可能与 IA 联系起来。

---

另外你截图下面这句也很有意思：

> “For array testability, a NO corresponds to an array word which was never read.”

也就是说，对于 memory/array：

```text
array[10] ← fault
     │
     │
workload 从来没有 read array[10]
     ↓
fault effect 没机会到 observation point
     ↓
NO
```

这实际上和上面的 NAND 例子是同一个思想：**不是 fault 不存在，而是 workload 没有给 fault 提供可观察的传播路径。**
